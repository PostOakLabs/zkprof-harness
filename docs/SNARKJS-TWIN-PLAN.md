# SnarkJS Independent-Twin Plan (2026-09-01)

Per the maintainers' route decision: a second, pure-JS verifier that must AGREE with the
wasm one on real + mutated receipts (the adversarial-pair doctrine) — queued and
now scoped. **SKELETON ONLY.** No snarkjs implementation in this work order; the
plan + dumped artifacts make the next one cheap. The dumped vkey + public inputs
are in `crates/zkprof-verify/fixtures/groth16-vkey-public-inputs.json`
(regenerate: `cargo run -p zkprof-verify --bin dump`).

## What a pure-JS snarkjs verification needs

1. **The Groth16 vkey.** snarkjs takes a vkey in its own JSON shape. The crate
   embeds `risc0_groth16::VerifyingKey` (the ceremony). `dumped_verifier_params()`
   serializes `Groth16ReceiptVerifierParameters` (control_root, bn254_control_id,
   verifying_key) to JSON. The twin must **convert** that verifying key into
   snarkjs' vkey shape (alpha/beta/gamma/delta/IC points). This is the highest
   divergence-risk step: the two verifiers must interpret the same
   `verifying_key` bytes as the same points.

2. **The public-input vector.** snarkjs verification takes the same five public
   inputs the risc0 on-chain verifier uses:
   `[control_root_hi, control_root_lo, claim_hi, claim_lo, bn254_control_id]`.
   The derivation (already working in-crate, `public_inputs_for`) is:
   - journal digest = sha256(JCS-canonical bytes of the receipt `journal`) — the
     confirmed byte contract (JOURNAL-BYTES-HYPOTHESIS).
   - claim = `ReceiptClaim::ok(image_id, journal_bytes)`; claim digest =
     `ReceiptClaim::ok(image_id, journal_digest).digest()`.
   - splitDigest(d) = reverse the 32-byte digest, then take the two 16-byte
     halves (this is the byte order the `RiscZeroGroth16Verifier.sol` uses).
   - The bn254_control_id is used whole (single uint256).
   The crate derives these and they are dumped per fixture.

3. **The seal as a snarkjs proof.** The Groth16 seal (256 bytes = `(a, b, c)` on
   BN254) must be deserialized into snarkjs' proof form (a, b, c points in the
   right field/format). The pair check is the same curve + pairing the crate uses.

4. **Claim-digest constant.** snarkjs needs the pairing = the proof over the
   claim digest (the `claim_digest` dumped). The twin must reproduce the exact
   `ReceiptClaim` digest algorithm (not merely the journal sha256) — that is the
   security-critical part.

## Where divergence risk concentrates

| Step | Risk | Why |
|---|---|---|
| vkey conversion (risc0 key → snarkjs key) | **highest** | Both must agree on point serialization (compressed/uncompressed, field element byte order). A wrong conversion is an adversarial-pair failure. |
| splitDigest byte order | high | The Solidity verifier reverses the digest before splitting; getting this backwards yields a valid-looking proof over the wrong public inputs. |
| claim-digest construction | high | `ReceiptClaim::ok` includes exit code + pre/post system state, not just image_id + journal digest. Reproducing it wrong = a "valid" receipt accepted for the wrong claim. |
| seal (a,b,c) deserialization | medium | G1/G2 point parsing; the 256-byte layout must map to snarkjs' expected packing. |
| journal bytes (JCS) | low now | CONFIRMED (RFC 8785 / JCS-canonical), so the twin uses the same canonicalizer. |

## Method for the next work order (recommendation)

1. Implement the snarkjs twin in Node (no npm install; vendored snarkjs if needed
   per the zero-egress rule) using the dumped vkey + public inputs.
2. Validate against the **same fixture receipts and the same mutations** the
   crate's tests use (`tests/hypothesis.rs`): real receipts must verify PASS,
   tampered seal / journal / imageId must FAIL.
3. The wasm verifier and the snarkjs twin must AGREE on every case. Any
   disagreement is estate-triage material (one of the two is wrong) — do not
   resolve unilaterally.
4. Because route (a) is a hand-embedded ceremony (not generated by snarkjs), the
   vkey-conversion correctness is best established by cross-validating the twin
   against the wasm verifier on a fixed vector before trusting either.
